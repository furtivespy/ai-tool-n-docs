# Stage 04: Manual / Integration QA & QA Loop (Steps 5–6)

Validates the running bot or app at the depth defined by [profiles.md](../profiles.md) and writes the canonical QA status block required by [05-merge-gate.md](05-merge-gate.md).

## Depth Resolution

Determine `qa_depth` from the (possibly escalated) `profile` and `capabilities.live_discord_qa` in [registry.yaml](../registry.yaml):

| Condition | `qa_depth` |
| --- | --- |
| `capabilities.live_discord_qa == false` | `skip` (`non-discord-repo`) |
| `profile == docs` (verified docs-only diff) | `skip` (`docs-only`) |
| `profile == maintenance` AND diff touches only tests/tooling/docs (no deps or runtime code) | `skip` (`non-runtime-maintenance`) |
| `profile == maintenance` (dependency bumps or runtime code edits on Discord bot) | `smoke` |
| `profile == standard` | `normal` |
| `profile == high-risk` | `regression` |

## Path A: `qa_depth == skip`

1. Verify the diff satisfies the exemption condition above (escalate to `smoke` or `normal` if runtime code changed unexpectedly).
2. When the PR uses the repo template with `<!-- qa-status:start --> ... <!-- qa-status:end -->`, rewrite that block on the PR description:
   - `Verdict:` `PASS`
   - `Depth:` `skip (<reason>)`
   - `Head:` `<exact full headRefOid>`
   - `Verified:` `<CI test/lint summary>`
   - `For you to test:` `none`
   - `User call-out:` `none`
3. Advance directly to Step 7 ([05-merge-gate.md](05-merge-gate.md)) if `capabilities.ship_pr == true`, else Step 8 ([06-post-ship.md](06-post-ship.md)) for `In Review` handoff.

## Path B: Live QA (`smoke` | `normal` | `regression`) via QA Department

Orchestrator dispatches **QA Department** (`grok-box`) with: `github_repo`, `pr_url`, `branch`, exact `head_sha`, `qa_depth`, `linear_url` + `Change` / `Done when` items, and Step 3's `notable_risks`. Keep Linear `In Progress`. When triggered from a `t3-local` PR carrying `ready-for-qa`, Grok CTO removes `ready-for-qa` on dispatch (preventing duplicate sends) and later forwards QA's reply back to the T3 webhook (`stage: "merge_gate"` on `QA: PASS` for `ship_pr: true`, or `stage: "fix"` on `QA: FAIL` with `t3_thread_id` from `<!-- workflow:qa-handoff -->`).

### Test Scope by Depth
- **`smoke`:** Check out exact `head_sha`, boot local bot with test token, confirm clean startup + `/ping` or `/status` response in the designated test channel with zero error logs, then stop local bot.
- **`normal`:** Run `smoke` plus every `Done when` item and reviewer `notable_risks` live in Discord (commands, interactions, buttons/selects, embeds); capture screenshots.
- **`regression`:** Run `normal` plus adjacent commands/flows, permission tiers, invalid inputs, and error recovery paths; capture screenshots.

### QA Guardrails
- Test only with the designated local test bot token (from local env/secret file; never printed or committed).
- Test only in designated test servers/channels.
- Check out the PR branch at `head_sha`, run, and observe; leave code untouched and never push or merge.
- Stop the local bot process when finished.

### Required Outputs (All Three)
1. **PR Comment (`## QA`):** Depth executed, exact `head_sha`, steps tested, results, and attached screenshots.
2. **PR Description Block:** Rewrite everything between `<!-- qa-status:start -->` and `<!-- qa-status:end -->` (when present):
   - `Verdict:` `PASS` | `FAIL`
   - `Depth:` `smoke` | `normal` | `regression`
   - `Head:` `<exact full headRefOid>`
   - `Verified:` `<concise summary of what passed>`
   - `For you to test:` `none` | `<concrete items only human can test>`
   - `User call-out:` `none` | `<release-note / user-facing break warning>`
3. **Orchestrator Reply:** Start with `QA: PASS`, `QA: FAIL`, or `QA: BLOCKED`, followed by `head_sha`, concrete repro steps (on `FAIL`), missing requirement (on `BLOCKED`), and screenshot URLs.

## Routing

- **`QA: PASS`:**
  - If `capabilities.ship_pr == true`: advance to Step 7 ([05-merge-gate.md](05-merge-gate.md)).
  - If `capabilities.ship_pr == false`: advance to Step 8 ([06-post-ship.md](06-post-ship.md)) as `ready_for_will`.
- **`QA: FAIL` & `pass < 6`:** increment `pass` (`pass + 1`) and loop back to Step 2 ([02-implement.md](02-implement.md)) with QA's concrete failures and repro steps. Stay silent in Discord and owner chat.
- **`QA: FAIL` & `pass == 6`:** route to the **loop-capped handoff** in [06-post-ship.md](06-post-ship.md). Start no 7th pass.
- **`QA: BLOCKED`:** ask QA once for what it needs (missing env var, test fixture, sign-in); if still blocked after one retry, escalate to owner in chat and leave Linear `In Progress` (never mark passed).

## Completion Criterion

Either the PR's `<!-- qa-status -->` block and `## QA` comment reflect the current `head_sha` with a clear `PASS` / `FAIL` verdict, or a `QA: BLOCKED` escalation was sent to the owner.
